# djoser 接口自动化测试计划

> 被测对象：`sunscrapers/djoser` 2.3.x
> 测试类型：黑盒接口测试（HTTP 层）+ 白盒源码定位
> 测试框架：pytest 8/9 + pytest-django + requests + jsonschema
> 报告周期：随上游发布节奏同步回归（CI 配置了每周定时回归）

---

## 一、测试目标

1. **验证功能正确性**：djoser 提供的账号生命周期接口（注册、登录、Token、密码、用户名）
   在真实 HTTP 调用下的行为是否符合其文档与接口契约。
2. **验证健壮性**：异常输入、类型错误、边界值、恶意载荷下，接口是否稳定降级
   （返回可处理的 4xx）而非抛出未捕获异常（500）。
3. **验证配置健壮性**：框架在**非默认配置组合**下是否仍能正常工作。
   这是本项目发现问题的主要来源。
4. **验证并发正确性**：唯一性约束、Token 幂等性在并发下是否成立。
5. **产出可复现的缺陷证据**：每个缺陷都有最小复现路径、真实响应、源码行级根因。

## 二、测试范围

### 2.1 纳入范围

| 模块 | 端点 | 说明 |
| --- | --- | --- |
| 用户注册 | `POST /auth/users/` | 正常注册、唯一性、必填、类型、边界、注入 |
| 登录 | `POST /auth/token/login/` | 凭据校验、防用户枚举、响应契约 |
| Token 登出 | `POST /auth/token/logout/` | Token 失效验证 |
| 当前用户 | `GET /auth/users/me/` | 鉴权边界、敏感字段泄露 |
| 密码修改 | `POST /auth/users/set_password/` | 改密、旧密码失效、弱密码 |
| 密码重置 | `POST /auth/users/reset_password/` | 端到端重置链路 |
| 密码重置确认 | `POST /auth/users/reset_password_confirm/` | 令牌校验 |
| 用户名修改 | `POST /auth/users/set_username/` | 改密、唯一性、边界 |
| 用户名重置 | `POST /auth/users/reset_username/` | 触发重置 |
| 用户名重置确认 | `POST /auth/users/reset_username_confirm/` | 令牌校验 |
| 配置矩阵 | 全部 | `LOGIN_FIELD` 与 `USERNAME_FIELD` 不一致场景 |
| 响应契约 | 全部 | JSON Schema 一致性 |
| 并发 | 注册 / 登录 / 改名 | 唯一性、幂等、脏写 |

### 2.2 排除范围

- **WebAuthn 认证**（`djoser.webauthn`）：需要硬件密钥模拟器，环境不具备
- **Social auth**（`djoser.social`）：需要第三方 OAuth Provider 凭据
- **JWT Token 模式**（`djoser.urls.jwt`）：需额外依赖 `djangorestframework-simplejwt`，
  与 Token 模式行为高度重叠，本期不纳入
- **SMTP 真实投递**：使用 Django `locmem` 后端，只验证邮件内容，不验证投递
- **性能压测**：本期不做基准测试（缺少可比基线，结论不可靠）

## 三、测试环境

| 项 | 配置 |
| --- | --- |
| 操作系统 | Windows 10 10.0.26200 x64 |
| Python | 3.11.7（CI 覆盖 3.10 / 3.11 / 3.12） |
| Django | 5.2.19 |
| djangorestframework | 3.x |
| djoser | 2.3.x |
| 数据库 | SQLite（文件型，见下） |
| 服务形态 | Django LiveServer（真实 WSGI 栈 + 真实 HTTP 端口） |

### 3.1 数据库选型说明

测试库使用**文件型 SQLite** 而非 `:memory:`。

原因：`:memory:` 数据库在 SQLite 中**按连接隔离**，每个连接看到各自独立的空库。
Django 的 LiveServer 在独立线程处理请求，会建立自己的数据库连接，
导致主线程通过 ORM 创建的用户在服务线程**不可见** ——
表现为"刚创建的用户立刻登录却提示凭据无效"的诡异现象。

改用文件型 SQLite 后所有连接指向同一文件，数据天然共享，
既避开线程隔离问题，也让并发用例成为可能。

## 四、测试策略

### 4.1 用例设计方法

| 方法 | 应用场景 | 举例 |
| --- | --- | --- |
| 等价类划分 | 输入合法性 | 有效值 / 空值 / null / 类型错误 / 非法枚举 |
| 边界值分析 | 长度与数量限制 | 用户名超长、密码长度下限、分页与批量上限 |
| 场景法 | 业务链路 | 注册→登录→改密码→改用户名→登出 完整生命周期 |
| 状态迁移 | 认证态变化 | 未认证 → 已认证 → Token 失效 |
| 错误推测 | 非常规路径 | `LOGIN_FIELD ≠ USERNAME_FIELD` 配置组合 |
| 判定表 | 组合条件 | 登录字段 × 密码正确与否 |

### 4.2 测试分层与标记

| 标记 | 含义 | 执行时机 |
| --- | --- | --- |
| `smoke` | 冒烟，每轮必跑 | 每次提交 |
| `contract` | 接口契约与 Schema 一致性 | 每次提交 |
| `negative` | 异常与非法输入 | 每次提交 |
| `boundary` | 边界值 | 每次提交 |
| `regression` | 缺陷回归锁 | 每次提交 |
| `concurrency` | 并发与幂等 | 每次提交（CI 额外重复 3 轮检测偶发） |
| `slow` | 需启动子进程 | 每次提交 |

### 4.3 测试隔离策略

- **数据隔离**：所有账号使用 UUID 派生的唯一用户名，**用例间零共享**，
  不依赖执行顺序，可任意并行或单跑
- **状态隔离**：每个用例通过 `pytest-django` 的事务回滚清理数据库
- **配置隔离**：配置矩阵测试通过**独立子进程**实现物理隔离
  （原因见「测试方法论」章节）
- **探针隔离**：同一探针内的多端点探测使用**独立账号**，
  避免改名等写操作污染后续探测

### 4.4 断言原则

全部断言基于**外部可观测行为**（HTTP 状态码、响应体、响应头），
不依赖数据库直查，保证测的是"第三方使用者实际能观察到的契约"，
而非"实现细节"。唯一例外是并发改名用例需要验证最终落库状态，
此时才查库确认无脏写。

## 五、缺陷管理

| 阶段 | 做法 |
| --- | --- |
| 发现 | 用例失败 + 服务端堆栈定位 |
| 确认 | 排除误报（配置问题、期望值错误），必须实际执行复现 |
| 定位 | 白盒读源码，定位到**具体行号**，分析根因 |
| 记录 | 写入 `docs/缺陷报告.md`，含复现步骤、实际/预期结果、根因、修复建议 |
| 回归 | 转为 `xfail(strict=True)` 用例锁定；上游修复后 XPASS 会导致 CI 失败，提醒移除标记 |
| 上报 | 向上游仓库提交 issue，附最小复现脚本与根因分析 |

**经验**：本项目共发现 3 个真实缺陷 + 2 个行为观察项。其中 BUG-01 与上游
issue #922 重复，但因该 issue 未实际执行验证，本项目提供了可执行的复现证据与
第二个触发点；BUG-02 为本项目新发现。

## 六、退出标准

一次回归通过的判定标准：

1. 所有非 `xfail` 用例全部通过
2. `xfail` 用例仍为 xfail（若出现 XPASS，说明上游已修复，需更新用例与缺陷报告）
3. 并发用例在 CI 中连续 3 轮通过（排除偶发性）
4. 无新增未登记缺陷

## 七、风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 上游 djoser 版本升级导致行为变化 | 用例误报 | CI 配置定时回归，失败时先比对版本差异 |
| SQLite 并发写锁限制 | 并发用例不稳定 | 已用文件型 SQLite；CI 中并发用例重复 3 轮检测偶发 |
| LiveServer 守护线程退出竞态 | CI 退出码非零 | conftest 中会话级 fixture 做 flush 与回收 |
| 上游不接受 issue | 缺陷无法闭环 | 缺陷报告独立成文，附完整复现路径，可直接提交 |
