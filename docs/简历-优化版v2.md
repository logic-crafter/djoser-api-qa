## 一、先看你原版的三个问题

### 问题 1：有句残留数据混在里面（必须删）

测试设计那一行末尾的：

> ~~编写63条用例，覆盖13个接口，按冒烟/契约/功能/参数校验/边界/场景/一致性/外部依赖8个维度分组，支持按维度筛选执行。~~

放在简历里会让人以为你有两个项目拼在一起，或者数字对不上 —— 面试官一追问就露馅。**必须删掉。**

### 问题 2：日期错了

`2026.04-2026.05` 是你原简历里「影评情感分析系统·接口自动化测试」的时间。
djoser 这个项目实际是 **2026.11** 做的，而且还在持续。
写成 4-5 月会和另一个项目撞车，面试官问"这两个项目同时做？"答不上来。

### 问题 3：信息过载（你说的"乱"）

原版「测试设计」那一段里同时塞了：
- 5 种用例设计方法
- 3 类验证手段（Schema / 并发 / Playwright）
- 8 个模块的分组说明
- 负向用例占比

**一段话里 5 层信息,读者大脑会直接放弃。** 简历不是技术文档,是给人 15 秒内形成印象的。

同样,「框架实现」里"框架在模块导入期固化配置,运行期覆盖无效"这种括号解释,
是**面试时展开讲的料**,不该占简历版面。

## 五、精简的取舍原则

简历项目经历要的不是"技术全貌"，而是**让面试官想问**。

| 该留在简历 | 该留给面试 | 该删掉 |
| --- | --- | --- |
| 数字：70 条 / 8 个接口 / 208 秒 | 为什么用独立子进程 | "框架在模块导入期固化配置" |
| 根因定位到行：`views.py:269` | 怎么定位到的 | 括号里的原理解释 |
| issue 链接可验证 | 怎么发现第二触发点 | 复现脚本细节 |
| 用到的技术栈 | Playwright 与 ORM 的冲突 | "原生 sync API 自建 fixture" |
| | 用例设计的完整 5 种方法 | 分组维度的完整枚举 |

判断标准：**这句话是"结果"还是"过程"？** 结果留简历，过程留面试。
技术细节是证明你会的证据，但成果才是让人想约你的理由。
