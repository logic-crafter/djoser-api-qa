## BUG-01 · 改用户名接口在非常规登录字段配置下抛出未捕获 `KeyError`

### 摘要

当 `DJOSER["LOGIN_FIELD"]` 与用户模型的 `USERNAME_FIELD` 不一致时，
`POST /auth/users/set_username/` 与 `POST /auth/users/reset_username_confirm/`
会抛出未捕获的 `KeyError`，返回 HTTP 500。

### 严重级别

**严重**。触发前提是生产中相当常见的配置（用户模型用 `username` 作唯一标识，
但希望支持邮箱登录）。一旦命中，账号管理接口完全不可用，且 500 会连带触发
监控告警与前端重试风暴。

### 复现步骤

1. 配置 `DJOSER = {"LOGIN_FIELD": "email"}`，用户模型保持 Django 默认
   （`USERNAME_FIELD = "username"`）
2. 创建用户并获取 Token
3. 以登录态调用 `POST /auth/users/set_username/`，请求体
   `{"new_email": "changed@example.com", "current_password": "..."}`

### 实际结果

```
HTTP 500 Internal Server Error

服务端抛出：
  File "djoser/views.py", line 269, in set_username
    new_username = serializer.data["new_" + User.USERNAME_FIELD]
  KeyError: 'new_username'
```

第二个触发点 `reset_username_confirm`：

```
  File "djoser/views.py", line 296, in reset_username_confirm
    new_username = serializer.data["new_" + User.USERNAME_FIELD]
  KeyError: 'new_username'
```

### 预期结果

改用户名接口要么正常工作，要么返回 400 校验错误，不应返回 500。

### 根因分析

缺陷源于**同一语义在框架内两层使用了不同的配置源**：

**序列化器层**（`djoser/serializers.py:259-263`）按 `settings.LOGIN_FIELD` 取字段：

```python
def __init__(self, *args, **kwargs):
    super().__init__(*args, **kwargs)
    self.username_field = settings.LOGIN_FIELD          # ← 配置 A
    self._default_username_field = User.USERNAME_FIELD
    self.fields[f"new_{self.username_field}"] = self.fields.pop(self.username_field)
```

当 `LOGIN_FIELD = "email"` 时，序列化器暴露的字段名是 **`new_email`**。

**视图层**（`djoser/views.py:269` 与 `:296`）却硬编码用 `User.USERNAME_FIELD` 取值：

```python
new_username = serializer.data["new_" + User.USERNAME_FIELD]   # ← 配置 B
```

`User.USERNAME_FIELD` 仍是 `"username"`，因此视图去取 `serializer.data["new_username"]`，
而序列化器里只有 `new_email` → `KeyError` → 未捕获异常 → 500。

值得注意的是，`UsernameSerializer.save()`（`serializers.py:265-270`）其实**已经写好了
兼容处理**：

```python
def save(self, **kwargs):
    if self.username_field != self._default_username_field:
        kwargs[User.USERNAME_FIELD] = self.validated_data.get(f"new_{self.username_field}")
    return super().save(**kwargs)
```

但视图**从未调用 `serializer.save()`**，而是直接从 `serializer.data` 取值再手动
`setattr` + `save()`，导致这段兼容逻辑完全失效。这是缺陷能长期存在的原因。

### 影响面

- 受影响端点：`/users/set_username/`、`/users/reset_username_confirm/`
- 受影响配置：任何 `LOGIN_FIELD != User.USERNAME_FIELD` 的部署
- 业务影响：使用邮箱登录的用户无法修改用户名；接口返回 500 而非可处理的 4xx

### 修复建议

**方案 A（推荐）**：让视图层与序列化器层使用同一个配置源。

```python
# djoser/views.py
@action(["post"], detail=False, url_path=f"set_{User.USERNAME_FIELD}")
def set_username(self, request, *args, **kwargs):
    serializer = self.get_serializer(data=request.data)
    serializer.is_valid(raise_exception=True)
    user = self.request.user
    new_username = serializer.data[f"new_{settings.LOGIN_FIELD}"]
    setattr(user, User.USERNAME_FIELD, new_username)
    user.save()
    ...
```

**方案 B**：改为走 `serializer.save()`，直接复用已有的兼容 shim。

### 与上游 Issue #922 的关系

上游 issue #922 由 `krishna3554` 于 2026-08-26 提出，作者在正文中明确写道：

> *This report is based on static analysis of master; I have not executed the code.*

即**仅做静态分析、未实际执行**。本项目通过真实 HTTP 请求 + 真实 WSGI 栈**实际执行复现**，
并补充了原文未覆盖的两点：

1. `reset_username_confirm` 作为**第二个独立触发点**被实际验证
2. 排除了"客户端传错字段名"这一可能 —— 实测传入视图层期望的 `new_username`
   同样返回 500，证明问题完全在服务端内部

## BUG-02 · 用户注册接口在非常规登录字段配置下抛出未捕获 `TypeError`

### 摘要

当 `DJOSER["LOGIN_FIELD"] = "email"` 时，`POST /auth/users/` 注册接口抛出未捕获的
`TypeError`，返回 HTTP 500。该问题**在上游 issue #922 中未被提及**，是本项目
在配置矩阵测试中新发现的。

### 严重级别

**严重**。注册是账号体系的入口，接口 500 意味着该配置下**新用户完全无法注册**，
配置实际处于不可用状态。

### 复现步骤

1. 配置 `DJOSER = {"LOGIN_FIELD": "email"}`，用户模型为 Django 默认 User
2. 调用 `POST /auth/users/`，请求体
   `{"username": "newuser", "email": "newuser@example.com", "password": "..."}`

### 实际结果

```
HTTP 500 Internal Server Error

服务端抛出：
  File "djoser/views.py", line 134, in perform_create
    user = serializer.save(*args, **kwargs)
  ...
  File "djoser/serializers.py", line 48, in perform_create
    user = User.objects.create_user(**validated_data)
TypeError: UserManager.create_user() missing 1 required positional argument: 'username'
```

### 预期结果

要么明确拒绝该配置组合（启动时校验或返回 400），
要么把 `username` 一并纳入可写字段，使注册正常工作。

### 根因分析

`djoser/serializers.py:62-68` 动态计算可写字段：

```python
class Meta:
    model = User
    fields = tuple(User.REQUIRED_FIELDS) + (
        settings.LOGIN_FIELD,       # ← "email"
        settings.USER_ID_FIELD,
        "password",
    )
```

Django 默认 User 模型的 `REQUIRED_FIELDS = ("email",)`，`USERNAME_FIELD = "username"`。
当 `LOGIN_FIELD = "email"` 时，`fields` 计算结果为
`("email", "id", "email", "password")` —— **`username` 完全不在可写字段中**。

于是 `validated_data` 里没有 `username`，而 `UserManager.create_user()` 的签名
要求 `username` 为必需位置参数，最终抛出 `TypeError`。

注意：由于 `Meta.fields` 在**类定义时（模块导入时）**就被求值为静态元组，
运行期修改 `DJOSER` 配置**不会**让该字段重新计算。这正是本项目必须用
**独立子进程**做配置矩阵测试的原因（详见测试方法论文档）。

### 影响面

- 受影响端点：`POST /auth/users/`
- 受影响配置：所有 `LOGIN_FIELD != User.USERNAME_FIELD` 的部署
- 业务影响：该配置下注册链路完全不可用

### 修复建议

**方案 A（推荐）**：注册时始终包含 `User.USERNAME_FIELD`。

```python
class Meta:
    model = User
    fields = tuple(User.REQUIRED_FIELDS) + (
        User.USERNAME_FIELD,        # ← 始终包含
        settings.LOGIN_FIELD,
        settings.USER_ID_FIELD,
        "password",
    )
```

**方案 B**：在 djoser 启动时校验配置合法性，对不支持的组合快速失败：

```python
if settings.LOGIN_FIELD != User.USERNAME_FIELD and settings.LOGIN_FIELD not in User.REQUIRED_FIELDS:
    raise ImproperlyConfigured(
        "LOGIN_FIELD must be either USERNAME_FIELD or a member of REQUIRED_FIELDS"
    )
```

方案 B 的价值在于把"运行时 500"变成"启动即报错"，对使用方更友好。

### 与 BUG-01 的关系

BUG-01 与 BUG-02 是**同一配置组合下的两类不同失败**，共同指向一个结论：

> `LOGIN_FIELD ≠ USERNAME_FIELD` 这一配置组合在 djoser 中**整体不可用**：
> 注册崩溃（BUG-02）、改用户名崩溃（BUG-01）、邮箱登录失败（认证后端不匹配）。

它们分别位于序列化器的**字段计算**与**字段读取**两个环节，修复需要同时覆盖。

## BUG-03 · `USERNAME_RESET_CONFIRM_URL` 未在默认配置中声明

### 摘要

`djoser/email.py:161` 引用了 `settings.USERNAME_RESET_CONFIRM_URL`，但该键
**不在 `djoser/conf.py` 的 `default_settings` 中**。

### 复现步骤

1. 使用默认配置（不显式提供该键）
2. 调用 `POST /auth/users/reset_username/`

### 实际结果

```
HTTP 500 Internal Server Error

服务端抛出：
  File "djoser/email.py", line 161, in get_context_data
    context["url"] = settings.USERNAME_RESET_CONFIRM_URL.format(**context)
AttributeError: 'Settings' object has no attribute 'USERNAME_RESET_CONFIRM_URL'
```

### 预期结果

返回 400 提示缺少必要配置，或在框架启动时即给出明确的配置缺失提示。

### 影响与说明

与 `PASSWORD_RESET_CONFIRM_URL` 一样，这是使用方需要提供的配置项。
但两者的处理方式不一致：`PASSWORD_RESET_CONFIRM_URL` 在 djoser 官方文档中
有明确说明，而 `USERNAME_RESET_CONFIRM_URL` 未在默认配置中声明，
导致用户漏配时得到的是一个语义不明的 `AttributeError` 500，
而非清晰的配置错误提示。

**严重级别**：一般（配置项，但错误提示不友好）。

**修复建议**：在 `default_settings` 中加入占位默认值，或在 `Settings` 初始化时
检测缺失项并抛出带明确说明的 `ImproperlyConfigured`。

## OBS-01 · 密码重置与用户名重置的路由命名规则不对称（观察项）

**现象**：

| 功能 | action 方法名 | 实际路由 |
| --- | --- | --- |
| 密码重置 | `reset_password` | `/users/reset_password/` |
| 用户名重置 | `reset_username` | `/users/reset_username/` |

但代码中，用户名重置显式重写了路由：

```python
@action(["post"], detail=False, url_path=f"reset_{User.USERNAME_FIELD}")
def reset_username(self, request, *args, **kwargs):
```

而密码重置**没有**重写。两者规则不一致带来的实际影响是：
当 `User.USERNAME_FIELD` 不等于 `"username"`（例如自定义用户模型用 `email` 作主标识）时，
用户名重置的路由会变成 `/users/reset_email/`，而密码重置仍是 `/users/reset_password/`。

这本身不一定是缺陷，但**同一功能族使用两套路由命名规则**，
增加了 API 使用者的认知成本，也让测试用例无法用统一规则推导路径
（本项目在编写用例时即踩中了这个坑：按 `password_reset` 猜测路径会得到 405）。

**建议**：统一命名规则，并在文档中明确列出所有端点路径。

## OBS-02 · `username` 传入整型时被隐式转换为字符串（观察项）

**现象**：`POST /auth/users/` 传入 `{"username": 12345}` 时，接口返回 **201**，
且创建出的用户名字符串为 `"12345"`。

**成因**：DRF 的 `CharField.to_internal_value()` 对非字符串输入执行 `str(data)` 转换，
属于框架的既定行为，**不是崩溃**。

**风险**：前端若误将用户 ID 等数字传入 `username` 字段，用户名会被静默转换成数字字符串，
业务上不易察觉。

**处理**：本项目将其作为**行为固化用例**（`test_register_numeric_username_coerced_to_string`）
而非缺陷，用例注释中说明了该风险。上游行为变更时可及时感知。

## 测试方法论补充

### 配置类缺陷必须在进程边界上验证

djoser 的 `UserCreateSerializer.Meta.fields` 在**模块导入时**就把
`settings.LOGIN_FIELD` 求值为静态元组。运行期用 `override_settings(DJOSER=...)`
修改配置**不会**让该字段重新计算。

本项目最初的实现尝试在同一 pytest 进程内切换配置，结果出现典型的
"单独跑通过、一起跑失败"现象 —— 根因是配置泄漏与进程内模块缓存。

**最终方案**：配置矩阵测试以 `subprocess` 启动独立 pytest 子进程，
通过 `DJANGO_SETTINGS_MODULE` 指向不同的 settings 模块，
子进程把观测结果写入 JSON 文件供父进程断言。

这不仅修复了测试本身，也让"配置类缺陷"获得了**进程边界级的可信复现**。

### 探针执行顺序必须避免自我污染

配置探针在一次运行中依次探测登录、注册、改名多个端点。
若把改名探测放在登录探测**之前**，改名会真实修改用户名，
导致后续用旧用户名登录必然失败，探针结果失真。

**对策**：登录探测前置；改名探测为每个字段名使用独立账号。

这一条是本项目调试过程中耗时最长的部分，记录于此以避免后续维护者重蹈覆辙。
