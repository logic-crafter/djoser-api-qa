### 缺陷根因分布

```
序列化器层与视图层使用不同配置源
├── BUG-01  字段读取不一致  → KeyError  (views.py:269 / :296)
└── BUG-02  字段计算遗漏    → TypeError (serializers.py:62-68)

配置项声明不完整
└── BUG-03  缺失 USERNAME_RESET_CONFIRM_URL → AttributeError (email.py:161)
```

**结论**：`LOGIN_FIELD ≠ USERNAME_FIELD` 这一配置组合在 djoser 中整体不可用，
注册、认证、改名三条主链路全部断裂，属于**配置层的系统性缺陷**而非单点疏漏。

## 三、测试方法论沉淀

本项目在执行过程中沉淀了三条可复用的测试方法结论，均已写入代码注释与文档：

### 3.1 配置类缺陷必须在进程边界上验证

`UserCreateSerializer.Meta.fields` 在**模块导入时**就把 `settings.LOGIN_FIELD`
求值为静态元组，运行期 `override_settings` 修改配置不会使其重新计算。

最初实现在同一 pytest 进程内切换配置，出现典型的"单独跑通过、一起跑失败"。
最终改为 `subprocess` 启动独立 pytest 子进程，以 `DJANGO_SETTINGS_MODULE` 指向不同
settings 模块，子进程把观测结果写入 JSON 供父进程断言。

> 收益：不仅修复了测试本身，更让配置类缺陷获得了**进程边界级的可信复现**。

### 3.2 探针执行顺序必须避免自我污染

配置探针在一次运行中探测多个端点。若改名探测排在登录探测之前，
改名会真实修改用户名，导致后续用旧用户名登录必然失败，探针结果失真。

> 对策：登录探测前置；改名探测为每个字段名使用独立账号。
>
> 这是本项目调试耗时最长的部分，记录于此以避免后续维护者重蹈覆辙。

### 3.3 数据库选型影响跨线程可见性

`:memory:` SQLite **按连接隔离**，LiveServer 线程的连接看不到主线程创建的数据，
表现为"刚创建的用户立刻登录却提示凭据无效"。

> 对策：改用文件型 SQLite，所有连接共享同一文件。文件名带进程号，
> 避免父子进程并发删除同一测试库导致 teardown 报错。

### 3.4 断言必须基于外部可观测行为

全部断言基于 HTTP 状态码、响应体、响应头，不依赖数据库直查，
确保验证的是"第三方使用者实际能观察到的契约"而非实现细节。

## 四、质量评估结论

### 4.1 djoser 在默认配置下的表现

**结论：质量良好。**

- 12 个端点在正常流程、非法输入、边界值、并发场景下行为一致，无崩溃
- 响应契约稳定，JSON Schema 校验全部通过
- 安全基线达标：
  - 错误凭据与未知用户返回**完全一致**的响应（防用户枚举）
  - 任何响应均不泄露密码或哈希算法标识
  - 错误响应是 JSON 而非 HTML 调试页
  - 登出后 Token 立即失效
- 并发正确性达标：唯一性约束、Token 幂等、无脏写

### 4.2 djoser 在非常规配置下的表现

**结论：存在系统性缺陷，配置组合整体不可用。**

`LOGIN_FIELD ≠ USERNAME_FIELD` 时，注册、认证、改名三条主链路全部断裂。
虽然该配置在生产中并不罕见（邮箱登录是常见需求），
但 djoser 既未在文档中明确声明不支持，也未在启动时快速失败。

### 4.3 改进建议优先级

| 优先级 | 建议 |
| --- | --- |
| P0 | 统一序列化器层与视图层的字段名来源（修复 BUG-01） |
| P0 | 注册字段计算始终包含 `User.USERNAME_FIELD`（修复 BUG-02） |
| P1 | 启动时校验 `LOGIN_FIELD` 合法性，不支持则 `ImproperlyConfigured` 快速失败 |
| P1 | 补齐 `USERNAME_RESET_CONFIRM_URL` 默认声明或给出明确配置提示（修复 BUG-03） |
| P2 | 统一 `reset_password` / `reset_username` 的路由命名规则（OBS-01） |
