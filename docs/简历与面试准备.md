## 二、面试问答准备

### Q1：为什么给一个第三方开源项目写测试？这跟测自己的项目有什么不同？

**回答要点**：

- 自建 Demo 后端测试，说服力在于"我懂 pytest"；但面试官会问：**这个 bug 是谁发现的？**
  自己写的代码自己测，缺陷天然是"预期内的"，缺乏真实缺陷挖掘能力的证明。
- 测真实开源项目，产出物是**可被第三方验证的**：GitHub issue 链接、PR、被 maintainer 回复，
  面试官点开就能查证，不需要听我自述。
- 真实项目还有真实项目才有的东西：版本兼容、配置组合、边界历史包袱。
  我在这个项目里发现的两个缺陷，都只在**特定配置组合**下才暴露 —— 这在自建 Demo 里根本测不出来。

### Q2：你说的两个 bug，具体是什么？为什么别人没发现？

**回答要点**：

- BUG-01：`LOGIN_FIELD="email"` 时，`POST /users/set_username/` 返回 500。
  根因是序列化器层用 `settings.LOGIN_FIELD` 取字段名（得到 `new_email`），
  视图层却硬编码 `User.USERNAME_FIELD`（去取 `new_username`）→ KeyError。
- BUG-02：同一配置下 `POST /users/` 返回 500。
  `UserCreateSerializer.Meta.fields` 用 `LOGIN_FIELD` 拼可写字段，
  导致 `username` 根本不在可写字段里，而 Django 默认 User 模型又要求它必填 → TypeError。
- **为什么别人没发现**：因为它只在 `LOGIN_FIELD ≠ USERNAME_FIELD` 时出现。
  大多数人用默认配置（两者都是 `username`），永远碰不到。
  我是通过**系统性做配置矩阵**（同一套探针在多套配置下跑）才撞上的 ——
  而不是随机试出来的。

### Q3：上游已经有人提了 issue #922，你的工作和它有什么区别？

**回答要点**（这题是加分点，要诚实且精确）：

- #922 的作者明确写了 *"This report is based on static analysis of master; I have not executed the code."*
  —— 是**纯静态分析**，没有实际跑起来。
- 我的差异：
  1. **实际执行复现**，给出真实 HTTP 500 与完整堆栈；
  2. 补上了原 issue 提到的**第二个触发点** `reset_username_confirm`（也实际验证了）；
  3. **排除了"客户端传错字段名"**这个可能 —— 我实测传 `new_username` 同样 500，
     证明问题完全在服务端内部；
  4. 指出了 `UsernameSerializer.save()` 里其实**已经写好了兼容 shim**，
     但视图从不调用 `serializer.save()`，所以 shim 失效 —— 这是缺陷能长期存在的原因。
- **我发现的 BUG-02 是全新的**，上游 issue 完全没有覆盖注册接口。

### Q4：你说的"独立进程边界验证"是什么意思？为什么必须这么做？

**回答要点**：

- djoser 的 `UserCreateSerializer.Meta.fields` 里写的是 `settings.LOGIN_FIELD`，
  但这个表达式在**模块导入时**就被求值，固化成一个静态元组了。
- 所以我在运行期用 `override_settings(DJOSER=...)` 改配置，
  **这个字段不会重新计算**，配置根本没生效。
- 一开始我就用同进程切换配置来写，结果出现很典型的现象：
  **单独跑通过，一起跑失败** —— 配置泄漏 + 模块缓存。
- 最终方案是用 `subprocess` 启动独立 pytest 子进程，
  通过 `DJANGO_SETTINGS_MODULE` 指向不同的 settings 模块，
  子进程把观测结果写成 JSON，父进程再断言。
- **这其实是我的一个方法论收获**：配置类缺陷必须在进程边界上验证，
  否则你测的可能根本不是你以为的那个配置。

### Q5：你的断言方式有什么讲究？

**回答要点**：

- 全部断言基于**外部可观测行为**：HTTP 状态码、响应体、响应头。
  不去直接查数据库断言 ORM 结果 —— 因为那是实现细节，
  测第三方使用者实际能观察到的契约才有意义。
- 唯一例外是并发改名的用例，需要查一次库确认最终状态没出现脏写，
  因为"最终落库成什么样"本身就是这个用例要验证的。
- 另外我特意做了**防用户枚举**的用例：错误口令和不存在的用户，
  必须返回**完全一致**的响应体，否则攻击者能据此批量探测有效账号。
  我先写了断言才发现 djoser 实际返回 400 而不是我预期的 401，
  然后回去读了源码确认 `INVALID_CREDENTIALS_ERROR` 是走 ValidationError，
  按框架既定行为校准了断言 —— 而不是直接改代码迁就我的错误预期。

### Q6：并发测试怎么做的？测出了什么？

**回答要点**：

- 用 `ThreadPoolExecutor` 起 8 个线程打真实 HTTP，不是 mock。
- 这也是我前面说的**文件型 SQLite** 的原因：
  `:memory:` 数据库在 SQLite 里是**按连接隔离**的，
  LiveServer 在独立线程处理请求、主线程通过 ORM 写数据，两边看到的是不同的库。
  一开始就踩了这个坑，症状是"刚创建的用户立刻登录却提示凭据无效"。
- 测了四个场景：并发注册同一用户名（应恰好 1 次成功，其余 400，不得有 500）、
  并发注册不同用户名（全部成功）、并发登录（应签发**唯一** Token，验证幂等）、
  并发改名（不得 500，最终值必须落在候选集内，验证无脏写）。
- 结果：**全部通过**。djoser 在并发下的正确性是没问题的 —— 这也是我敢在报告里
  下"默认配置下质量良好"这个结论的依据。

### Q7：你的测试套件怎么保证别人也能跑？

**回答要点**：

- `requirements.txt` 固定依赖，README 给了三条命令（跑全量 / 只跑配置矩阵 / 只跑并发）。
- 用例标记分了 8 类（smoke / contract / negative / boundary / concurrency / slow 等），
  可以按维度选跑。
- 全部 56 条用例实跑通过、耗时约 173 秒、无警告、退出码 0，CI 里可直接用。
- 数据隔离靠 UUID 唯一账号 + 事务回滚，**用例之间零共享**，任意顺序单跑都通过 ——
  我在调试时验证过这一点：单独跑某个用例和一起跑结果完全一致。

### Q8：如果让你继续做，你会补什么？

**回答要点**（展示规划能力）：

- **JWT 模式**（`djoser.urls.jwt`）：djoser 支持 JWT 和 Token 两种模式，
  我只测了 Token 模式，JWT 的刷新/失效语义不同，值得单独测。
- **WebAuthn**：需要模拟器，环境不具备，但这正是我列进"排除范围"并写明原因的部分 ——
  划清范围比假装覆盖更重要。
- **Fuzzing**：可以引入 `restler-fuzzer` 这类工具做状态化 API 模糊测试，
  我的配置矩阵思路和它有互补性：fuzzing 找"没见过的输入路径"，
  配置矩阵找"没被测过的配置组合"。
- **性能基线**：目前没做，因为缺可比基线，结论不可靠。等有了稳定版本序列再补趋势对比。
- **上游贡献**：CI 配置好了，等上游接受 PR 的反馈后，可以把回归用例直接合进 djoser 的
  测试套件，这对我的求职价值不如对社区大，但值得做。

## 三、面试官可能追问的硬骨头（提前准备）

### 追问 1：这些测试如果 djoser 升级了，会不会大面积失效？

会，而且这正是我想说的：**这类套件的价值不在"永远绿"，而在"变化能被立刻发现"**。
我配了每周定时回归，失败时第一件事就是比对版本 diff，
判断是"上游改了行为"（合理，需要更新断言）还是"引入了回归"（要报 issue）。
我的缺陷回归锁就是干这个的 —— 缺陷被修复时，断言会失败并提醒我更新用例和报告。

### 追问 2：你的项目有多少是你自己写的代码？

**要诚实**。测试用例是我写的，被测框架是别人的。
但要说清楚我的贡献边界：
- 56 条用例、7 个测试模块、配置矩阵测试框架（子进程探针 + JSON 结果回传）、
  测试环境配置、CI 流水线、4 份测试文档 —— 全是原创。
- 真正的工作量不在"写用例"，而在**让缺陷能被可信复现**：
  排查了进程边界问题、数据库跨线程可见性问题、探针执行顺序污染问题。
  这些是让 56 条用例真正有价值的部分。

### 追问 3：你怎么保证发现的不是误报？

三层过滤：
1. **源码交叉验证** —— 每个失败都去读源码确认是框架行为还是我的预期错了。
   事实上有 3 个用例最初失败是我的预期错（状态码 400 vs 401、
   整型参数被转字符串、弱密码未被拦截因为没配校验器），我按源码校准了断言。
2. **对照组设计** —— 配置矩阵测试里，每个非常规配置都有一个默认配置对照组，
   证明"是这个配置导致的"，而不是"这个接口一直有问题"。
3. **进程边界复现** —— 独立子进程排除了同进程配置污染与模块缓存的干扰。

### 追问 4：这个项目对标的高级测试工程师标准？

我不认为我到了资深水平。但我认为它证明了三件事：
- 能独立搭建一套完整的多层次接口测试工程（含契约、并发、配置矩阵）；
- 能读源码做根因定位到行，不止于"这个接口报错了"；
- 能把缺陷发现闭环到可被第三方验证的程度（issue 链接 + 复现脚本 + 根因分析）。
